BirdAlert | Python, Terraform, AWS

Live beta: birdalert.gatherer.tech | Source: GitHub — BirdAlert

AWS serverless application for collecting, processing and querying UK wildlife sightings. Phase 1 implemented and validated in a development environment in October 2026.

  • Implemented an ingestion pipeline in Python and Terraform: EventBridge schedules Lambda collection, S3 preserves raw eBird responses and a separate processor validates sightings for DynamoDB.
  • Used stable sighting identities and conditional transactional writes to make repeated processing idempotent. Excluded private sightings and retained explicit validation status for provisional records.
  • Built an indexed read API with region/species/date filters, cursor pagination and UK daylight-saving support; CloudFront serves the static client.
  • Added scoped IAM, Parameter Store, bounded retries, SQS dead-letter queues and CloudWatch alarms. Development checks covered ingestion and processor failure handling; Python tests cover processing and the API.
Architecture, implementation and verification details

Event-driven architecture and infrastructure

A 15-minute EventBridge heartbeat invokes the collector. Unique object keys preserve upstream response bytes in a private S3 bucket; S3 events invoke the processor. Terraform defines the application infrastructure, function-specific IAM roles, log groups and retention. API Gateway exposes the read API, and CloudFront serves the static client from a separate site bucket using Origin Access Control.

Data modelling, validation and idempotency

Processing validates response shape, coordinates, timestamps, privacy and optional counts. Submission/species hashes identify a sighting independently of the collection region. Batch identity reads avoid unnecessary writes; conditional DynamoDB transactions protect concurrent creation and maintain query records. Compact indexed records support latest, region, species and combined queries, trading extra writes and eventual consistency for bounded reads.

API design

The API defaults to ten results and caps requests at fifty. Cursor pagination bounds responses; UK calendar dates convert to UTC query ranges with daylight-saving handling. Database connectivity and the freshness of successfully processed data are separate health signals.

Security, observability and failure handling

Function-specific roles separate raw writes, processing and API reads; Parameter Store supplies the upstream API token. Upstream transient retries and Lambda asynchronous retries address different failure points. SQS dead-letter queues support investigation and manual replay; CloudWatch alarms and SNS provide operational notifications. CORS is not authentication, and throttling is not a hard spending limit. Queue retention cannot recover raw objects after their shorter S3 expiry.

Testing and recorded deployment evidence

Repository acceptance records dated 15 October 2026 cover development-environment ingestion/freshness and an injected processor failure reaching its dead-letter queue and alarm path. Python tests exercise processing and API behaviour; Terraform validation passed in the career-record review. That review recorded 45 of 46 Python tests passing, with a stale homepage-link assertion failing, plus a Terraform formatting issue in production variables. This is recorded development verification, not evidence of production-scale operation or a fully passing current suite.

Development process and current scope

Developed with agent assistance, human review and approval of material decisions. Phase 1 is the implemented scope. Personalised user alerts, watchlists, the replacement frontend and its proposed separate CI/CD repository remain planned or ongoing. Further poller, event-delivery and stale-processing failure simulations are not recorded as completed. The public beta is available above; its existence does not establish production-grade reliability.

Stormwatcher | Python, Terraform, AWS

github.com/adam-gatherer/stormwatcher

Built a weather-ingestion and risk-scoring pipeline: scheduled collection lands raw forecast data in S3, a second Lambda validates and transforms it, and DynamoDB stores the results. Implemented configurable SNS status and threshold notifications, with infrastructure defined in Terraform.

Separates collection from transformation, retaining the upstream JSON inside a metadata wrapper. Uses location/timestamp keys and converts Python floats to Decimal for DynamoDB. The source implements the pipeline and optional SNS notifications. Dated live acceptance and an automated test suite were not established in the career-record review. A read API, frontend, CloudWatch alarms and DynamoDB Streams remain roadmap work.

JIL Estate Sync | AWS, Terraform

AWS event-driven proof of concept for moving generated scheduler JIL snapshots through S3, EventBridge and CodeBuild into GitHub pull requests, with Terraform-managed IAM. Source

Proof-of-concept workflow and boundaries

An EC2 lab generates placeholder JIL, uploads it to versioned S3 and triggers CodeBuild through EventBridge. Bash compares the files, creates a branch and commit, and requests a GitHub pull request. Secrets Manager supplies the GitHub token; the script includes a no-change exit and optional reviewers.

Generated data avoids requiring a live scheduler, while pull requests provide a review boundary. This is personal proof-of-concept work, not a Barclays deployment or a completed real AutoSys exporter. Automated tests and dated end-to-end acceptance were not established.

Built a serverless CV website following the Cloud Resume Challenge, with S3/CloudFront hosting, a Python Lambda/DynamoDB visitor counter and a GitHub Actions workflow for site synchronisation and cache invalidation.

Hosting and deployment implementation

Static HTML/CSS/JavaScript is delivered through S3 and CloudFront. A separate Python Lambda reads and updates the DynamoDB visitor count. GitHub Actions synchronises the site directory, then invokes CloudFront invalidation; deployment credentials are held in repository secrets.
